# District migration checklist

These files are for a database that already has all `202610*` migrations. Apply SQL contents in Supabase SQL Editor in the order below. A Vercel deploy or `npm install` does **not** run them. First back up the database and private Storage bucket, and save the dry run's single result table. Obtain the owner's approval before applying steps 01–08 because they change production data and access rules.

After each step, check the SQL Editor success result. In staging, also query `pg_constraint`, `pg_policies`, and `pg_proc` for new objects. Do not apply later steps after an error. Capture the error and restore the last backup or repair in a reviewed transaction.

The dry run is only a report. **Step 05 is the documented data-changing archive step**: it soft-removes staff without a Panchayati Raj assignment from active login and hides non-Panchayati Raj historical attendance in the new portal. It does not delete historical attendance. Review the affected people and records before approving that step. Existing private file paths remain intact for old historical records; new uploads use `block_id/staff_id/date/file`.

Run the read-only `docs/STAFF_ARCHIVE_REVIEW.sql` before step 05 to inspect every active account that would be deactivated. The first district dry run on 2026-11-10 reported 106 such accounts, 141 non-Panchayati-Raj assignments, and one historical Agriculture attendance row. These counts are observations, not approval to archive.

For BPRO/DPRO password reset, edit only the relevant password in gitignored `private/seed-admins.json`, then run `node --env-file=.env.local scripts/seed-admins.ts --apply --rotate-passwords`. This rotates all ten entries, so supply current intended passwords for all of them. To change only one account, use Supabase Auth's administrator reset for that exact user after verifying its role and email, then record the change in the organization's secure credential register. Never commit or post passwords.

## Nine block workbook import

The files in `../STAFF DETAILS ALL BLOCK/` provide Araria, Bhargama, Forbesganj, Jokihat, Kursakanta, Narpatganj, Palasi, Raniganj and Sikti. Run `node scripts/prepare-block-rosters.mjs` to make the gitignored `private/block-roster-preview.json`; review its summary and issues. It skips vacancy rows, keeps staff with missing phone/gender as directory entries, and combines repeated assignments for the same name and phone within one block. Same-name/different-phone and same-phone/different-name rows remain separate and are flagged for review instead of being merged automatically.

After applying step 09, run `node scripts/import-block-rosters.mjs --blocks=forbesganj,narpatganj` for a read-only comparison, then add `--apply` to import just those two blocks. The `--blocks=` option accepts comma-separated block codes. Omitting it selects all blocks and may overwrite BPRO edits or reactivate previously removed roster rows. To replace the old Araria directory in a fresh setup, select `--blocks=araria --replace-araria` and review the dry run before adding `--apply`: that explicitly **soft archives former Araria `profiles`** (`active=false`, `deleted_at` set) and stops those old staff logins. The import preserves all attendance rows and private evidence. It creates no Auth users or staff passwords.
