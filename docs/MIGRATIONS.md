# District migration checklist

These files are for a database that already has all `202610*` migrations. Apply SQL contents in Supabase SQL Editor in the order below. A Vercel deploy or `npm install` does **not** run them. First back up the database and private Storage bucket, and save the dry run's single result table. Obtain the owner's approval before applying steps 01–08 because they change production data and access rules.

| Order | File                                  | Effect                                                                                                                                       | Verification                                                                                                                                          | Rollback note                                                                              |
| ----- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 00    | `20261109_00_district_dry_run.sql`    | Read-only counts by department, role, block, attendance and uploads.                                                                         | Save the result; compare totals to Supabase table counts.                                                                                             | None required.                                                                             |
| 01    | `20261109_01_blocks_roles.sql`        | Creates nine blocks, adds/backfills `block_id`, maps old admins to BPRO/DPRO, archives old role names, and gives holidays a block-aware key. | `select code,name_en from blocks order by code`; `select role,count(*) from profiles group by role`; all required `block_id` columns have zero nulls. | Restore database backup; changing role and key structures is not a safe one-line reversal. |
| 02    | `20261109_02_block_visibility.sql`    | Block-scoped RLS reads, bootstrap, change counters and leave balances.                                                                       | Sign in as one BPRO and check that cross-block rows are invisible; DPRO sees all.                                                                     | Restore prior policy and function definitions from backup.                                 |
| 03    | `20261109_03_block_writes_office.sql` | Guards block-consistent writes and scopes district/block holidays and notices.                                                               | Try a wrong-block write in a test transaction; it must fail.                                                                                          | Restore prior functions/triggers and backup.                                               |
| 04    | `20261109_04_district_rpc_roles.sql`  | Updates legacy RPC role checks and camera path validation.                                                                                   | Confirm BPRO/DPRO staff management and current attendance workflow in staging.                                                                        | Restore previous RPC definitions from backup.                                              |
| 05    | `20261109_05_department_archive.sql`  | Archives non-Panchayati-Raj assignments and deactivates staff with no Panchayati Raj assignment; retains every historical attendance row.    | Compare pre/post attendance row counts and the private department archive; confirm all active staff assignments are Panchayati Raj.                   | Restore backup or restore archived profile assignments after an explicit reviewed plan.    |
| 06    | `20261109_06_login_limits.sql`        | Adds account/IP keyed failed-login limits.                                                                                                   | Confirm a test account locks after repeated bad passwords and unlocks after the window.                                                               | Drop the new login-limit functions/table after reverting the application login handler.    |
| 07    | `20261109_07_move_staff.sql`          | Adds DPRO-only atomic staff transfer RPC; preserves historical attendance block.                                                             | Move a test staff account; check current block, assignments and unchanged old attendance block.                                                       | Move the test profile back through DPRO; restore function from backup if necessary.        |
| 08    | `20261109_08_block_workspaces.sql`    | Makes panchayat/workspace identity `(block_id,name)`.                                                                                        | Create same name in two blocks in staging and verify attendance references the right block.                                                           | Restore backup because reverting a composite key may collapse distinct names.              |

After each step, check the SQL Editor success result. In staging, also query `pg_constraint`, `pg_policies`, and `pg_proc` for new objects. Do not apply later steps after an error. Capture the error and restore the last backup or repair in a reviewed transaction.

The dry run is only a report. **Step 05 is the documented data-changing archive step**: it soft-removes staff without a Panchayati Raj assignment from active login and hides non-Panchayati Raj historical attendance in the new portal. It does not delete historical attendance. Review the affected people and records before approving that step. Existing private file paths remain intact for old historical records; new uploads use `block_id/staff_id/date/file`.

For BPRO/DPRO password reset, edit only the relevant password in gitignored `private/seed-admins.json`, then run `node --env-file=.env.local scripts/seed-admins.ts --apply --rotate-passwords`. This rotates all ten entries, so supply current intended passwords for all of them. To change only one account, use Supabase Auth's administrator reset for that exact user after verifying its role and email, then record the change in the organization's secure credential register. Never commit or post passwords.
